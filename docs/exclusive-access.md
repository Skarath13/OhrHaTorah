# Exclusive access (code-gated pages)

Skeleton for pages that only select people can open, using a shared code. No
sign-ups or accounts. Built October 31, 2026; inert until migration 0004 is
applied and real pages are added.

## How it works

1. Areas are listed in `exclusiveAreas` in `src/lib/exclusiveAccess.ts`. One
   area exists: `members` at `/members` (placeholder page only, not linked
   from navigation).
2. `src/middleware.ts` checks every request under an area prefix. Signed-in
   admins pass. Everyone else needs a valid access session, or is sent with a
   303 to `/access?area=members&next=/members/...`. Gated responses get
   `Cache-Control: private, no-store` and `X-Robots-Tag: noindex, nofollow`.
3. `/access` is a plain HTML form (works without JavaScript). It posts to
   `/api/access/unlock`, which checks the code, sets an HttpOnly cookie
   `oht_access_<area>` (SameSite=Lax, 30 days or until the code expires), and
   redirects back to the requested page. Redirect targets are restricted to
   paths inside the area.
4. Wrong codes are rate limited with the existing login limiter (5 tries, then
   15 minutes), in a separate `access:<ip>` bucket so member typos never lock
   the admin PIN login.
5. Anything unavailable (no D1, tables missing) fails closed: the page stays
   locked and the visitor sees "This area is not open yet."

## Codes

- Generated by the server: 10 characters from an unambiguous alphabet, shown as
  `XXXXX-XXXXX`. Case, spaces and dashes are ignored when typed.
- Only a SHA-256 hash is stored. The plain code is returned once, at creation.
- A code can carry an optional expiry. Sessions never outlive their code.
- Revoking keeps the row (audit) and deletes every session opened with it, so
  everyone using that code is locked out on their next page load.
- `use_count` and `last_used_at` show whether a code is being used.

## Admin API (admin role only; editors get 403)

All require the admin session cookie; POST and DELETE also need the
`X-CSRF-Token` header, same as the calendar admin.

| Method | Path | Body | Result |
|---|---|---|---|
| GET | `/api/admin/access-codes` | | `{ areas, codes }` (no hashes) |
| POST | `/api/admin/access-codes` | `{ area, label, expiresAt? }` | `{ id, code }`, plain code shown once |
| DELETE | `/api/admin/access-codes/:id` | | Revokes the code |

There is no admin screen yet. Next step is a small "Access codes" panel in the
admin toolbar: list, "Create code" (label + optional end date), copy/print, and
"Turn off".

## Database

Tables `access_codes` and `access_sessions`:
`deploy/chuck-staging/migrations/site/0004_exclusive_access_codes.sql`, also
added to `schema.sql` for brand-new databases. The migration is additive
(`CREATE ... IF NOT EXISTS` only) and touches no existing rows.

Per `docs/production-data-safety.md`, it has **not** been applied anywhere.
Apply it as its own reviewed operation: staging first, backup before
production, never as part of a code deploy.

## Adding a private section

1. Add `{ area: 'board', pathPrefix: '/board', title: 'Board' }` to
   `exclusiveAreas` (lowercase letters, digits, dashes).
2. Create pages under `src/pages/board/` and register them in `pageSections`
   in `PageLayout.astro`.
3. Create a code for the `board` area and hand it out.
